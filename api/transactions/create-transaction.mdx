---
title: 'Create Transaction'
openapi: 'POST /transactionmanagement/create-transaction'
description: 'Initiate a new remittance transaction using existing customer profiles.'
---

Initiates a new transaction where the sender and recipient have already been onboarded. Both must have active customer profiles.

## Request Headers

<ParamField header='X-Auth-Token' type='string' required>
  JWT Access Token of the authenticated user.
</ParamField>

<ParamField header='X-Idempotency-Key' type='string' required>
  A unique key for this transaction submission. If the same key is sent twice, the second request returns the result of the first rather than creating a duplicate transaction. Use a UUID or a unique reference from your system.
</ParamField>

<ParamField header='ipAddress' type='string' required>
  IP address of the device initiating the transaction.
</ParamField>

<ParamField header='platform' type='string' required default='fincode'>
  Platform identifier. Use `fincode`.
</ParamField>

<ParamField header='uuid' type='string' required default='200'>
  Unique request identifier.
</ParamField>

<ParamField header='password' type='string'>
  Optional. The password is not checked on create-transaction, so this header can be left out.
</ParamField>

## Request Body

<ParamField body='amount' type='number' required>
  The amount the recipient will receive, in the receiving currency.
</ParamField>

<ParamField body='sendAmount' type='number' required>
  The amount the sender pays, in the sending currency.
</ParamField>

<ParamField body='inclussive' type='boolean' required>
  Whether fees are included in `sendAmount`. Set to `true` if the sender pays a fixed amount inclusive of all fees; `false` if fees are added on top.
</ParamField>

<ParamField body='sendCurrency' type='string' required>
  ISO 4217 currency code the sender is paying in (e.g. `GBP`).
</ParamField>

<ParamField body='receivingCurrency' type='string' required>
  ISO 4217 currency code the recipient will receive (e.g. `NGN`).
</ParamField>

<ParamField body='type' type='string' required>
  Transaction / delivery method. Common values:

  | Value | Description |
  |-------|-------------|
  | `ACCOUNTPAYMENT` | Bank account transfer |
  | `MOBILE_MONEY` | Mobile money (e.g. M-Pesa) |
  | `CASHPICKUP` | Cash pickup at agent location |
  | `WALLET` | Wallet transfer |
</ParamField>

<ParamField body='transactionProcessingMode' type='string' required>
  Aggregation mode for the transaction. Accepted values: `NONE_AGGREGATION` and `AGGREGATION`. Use `NONE_AGGREGATION` for a standard transaction.
</ParamField>

<ParamField body='paymentMethod' type='string'>
  Accepted but not currently used. Whatever value is sent, cashier bookings are recorded as `CASHIER_PAY_FROM_CUSTOMER_E_WALLET`, and every booking starts as `PENDING_PAYMENT`. To pay for a booking from a wallet, call [Make Payment from Wallet](/api/deposit-engine/make-payment-from-wallet). A value that is not a valid payment method is rejected.
</ParamField>

<ParamField body='preExistingSenderCustomerCode' type='string'>
  Customer code of an existing sender (returned from `find-customer-by-name-or-phone-no` or `register-customer`). Required unless you send `newSenderKyc` to create a new sender in the same request. Send exactly one of the two. See [Agent Integration](/remittance/agent-integration) for the new sender option.
</ParamField>

<ParamField body='preExistingRecipientCustomerCode' type='string'>
  Customer code of an existing recipient/beneficiary (returned from `new-beneficiary`). Required unless you send `newRecipientKyc` to create a new recipient in the same request. Send exactly one of the two.
</ParamField>

<ParamField body='creditParty' type='array' required>
  Key-value pairs for the recipient's bank/account details. See the [Add Bank Details](/api/transactions/add-bank-details) key reference for the full list of valid keys. All keys must be lowercase.

  <Expandable title='creditParty item'>
    <ParamField body='key' type='string' required>
      Field key — must be lowercase. Common values: `bankname`, `bankaccountno`, `accountholdername`, `bankcode`, `swiftbic`, `sortcode`, `iban`.
    </ParamField>
    <ParamField body='value' type='string'>
      Field value.
    </ParamField>
  </Expandable>
</ParamField>

<ParamField body='internationalTransferInformation' type='object' required>
  Regulatory and routing information for the transfer.
  <Expandable title='internationalTransferInformation fields'>
    <ParamField body='originCountry' type='string' required>ISO 3166-1 alpha-3 code of the sender's country (e.g. `GBR`)</ParamField>
    <ParamField body='receivingCountry' type='string' required>ISO 3166-1 alpha-3 code of the recipient's country (e.g. `NGA`)</ParamField>
    <ParamField body='remittancePurpose' type='string' required>Purpose of the transfer (e.g. `FAMILY_SUPPORT`, `GIFT`, `EDUCATION`)</ParamField>
    <ParamField body='sourceOfFunds' type='string' required>Declared source of funds (e.g. `SALARY`, `SAVINGS`, `BUSINESS`)</ParamField>
    <ParamField body='relationshipSender' type='string'>Sender's relationship to the recipient (e.g. `PARENT`, `SPOUSE`, `FRIEND`)</ParamField>
  </Expandable>
</ParamField>

<ParamField body='securityQuestion' type='string'>
  Security question for cash pickup transactions. Required when `type` is `CASHPICKUP`.
</ParamField>

<ParamField body='securityAnswer' type='string'>
  Answer to the security question. Required when `type` is `CASHPICKUP`.
</ParamField>

<ParamField body='transactionReference' type='string'>
  Your own reference for this transaction. Optional — the platform generates one if not provided.
</ParamField>

<ParamField body='dynamicFields' type='object'>
  Additional dynamic fields specific to your configuration. Pass an empty object `{}` if not applicable.
</ParamField>

<ParamField body='eligibleDocumentList' type='array'>
  List of documents attached to this transaction (for transactions requiring document verification). Pass an empty array `[]` if none.
</ParamField>

## Code Example

```bash cURL

--header 'X-Auth-Token: YOUR_TOKEN' \
--header 'X-Idempotency-Key: a1b2c3d4-e5f6-7890-abcd-ef1234567890' \
--header 'ipAddress: 192.168.1.100' \
--header 'Content-Type: application/json' \
--header 'platform: fincode' \
--header 'uuid: 200' \
--data '{
  "amount": 150000,
  "sendAmount": 100,
  "inclussive": false,
  "sendCurrency": "GBP",
  "receivingCurrency": "NGN",
  "type": "ACCOUNTPAYMENT",
  "transactionProcessingMode": "NONE_AGGREGATION",
  "preExistingSenderCustomerCode": "VJJGVE",
  "preExistingRecipientCustomerCode": "BNADKO",
  "creditParty": [
    {"key": "bankname",          "value": "GTBank"},
    {"key": "bankaccountno",     "value": "0123456789"},
    {"key": "accountholdername", "value": "Ada Okonkwo"},
    {"key": "bankcode",          "value": "058"},
    {"key": "swiftbic",          "value": "GTBINGLA"}
  ],

    "originCountry": "GBR",

```

## Response

The response is returned as a plain object (not wrapped in `data`). On success, these fields carry values:

<ResponseField name='objectReference' type='string'>
  The payment reference number (PCN). Use it for payment and status calls such as `checktransactionstatus/{pcn}`.
</ResponseField>

<ResponseField name='serverCorrelationId' type='string'>
  The transaction ID.
</ResponseField>

<ResponseField name='payAbleId' type='string'>
  The transaction ID, for use as `payAbleId` in payment calls.
</ResponseField>

<ResponseField name='status' type='string'>
  `SUCCESS` when the transaction was created.
</ResponseField>

<ResponseField name='transactionStatus' type='string'>
  The transaction status, normally `PENDING_PAYMENT` for a new booking.
</ResponseField>

<ResponseField name='preExistingSenderCustomerCode' type='string'>
  The sender's customer code. Store it and reuse it for later bookings with the same sender.
</ResponseField>

<ResponseField name='preExistingRecipientCustomerCode' type='string'>
  The recipient's customer code. Store it and reuse it for later bookings with the same recipient.
</ResponseField>

<ResponseField name='userId' type='string'>
  The sender's user ID.
</ResponseField>

<ResponseField name='receivingAmount' type='number'>
  The amount the recipient will receive.
</ResponseField>

<ResponseField name='iso3CountryFrom' type='string'>
  ISO 3166-1 alpha-3 code of the sending country.
</ResponseField>

<ResponseField name='iso3CountryTo' type='string'>
  ISO 3166-1 alpha-3 code of the receiving country.
</ResponseField>

<ResponseField name='payableType' type='string'>
  `TRANSACTION`.
</ResponseField>

<ResponseField name='compliant' type='boolean'>
  Whether the transaction has passed its compliance checks.
</ResponseField>

<ResponseField name='complienceCheck' type='string'>
  Compliance check result: `PASS`, `WARNING`, `AWAITING_CUSTOMER_ACTION` or `FAIL`.
</ResponseField>

<ResponseField name='customerComplianceCheckList' type='array'>
  Compliance requirements linked to this transaction.
</ResponseField>

<ResponseField name='message' type='string'>
  `Transaction created successfully`.
</ResponseField>

Other fields in the response are not populated on success and come back empty (`null`, `0` or `false`). There are no fields named `pcn` or `customerCode`; the PCN is in `objectReference`.

### When compliance documents are required

If the booking cannot go ahead until the customer provides documents, no PCN is returned. The response carries `status` `FAILED`, `transactionStatus` `FAILED`, `errorCode` `-1`, `errorCodeType` `KYC_DOCUMENT_REQUIRED_502`, a `message` explaining the requirement, and `customerComplianceCheckList` listing what is needed. Collect the listed documents, then submit the booking again.
