    ## Step 1 - Customer Registration

    Registers a new customer account in the system. This endpoint is designed to reduce the number of API calls required from sign-up to KYC/AML submission. It presents the option to combine sign-up and KYC/AML documents into a single call. Call `list-organisation-compliance-policy` first to obtain your organisation's KYC/AML requirements and understand what to include. The endpoint:

    - Creates a customer profile with personal or company information
    - Validates and stores address information
    - Processes dynamic fields based on organisation configuration
    - Performs external screening validation for the registration country
    - Initiates compliance checks for the newly registered customer

    | Method | Path | What it does | Swagger |
    |--------|------|--------------|---------|
    | `POST` | [`usermanagement/register-customer`](/api/ciam/create-customer) [→](/api/ciam/create-customer) | Register a new sender | [↗](https://test-nucleus-engine.eks-fincode.com/swagger-ui/index.html?urls.primaryName=customer#/user-management/registerCustomer) |
    | `GET` | [`usermanagement/profile`](/api/ciam/profile) [→](/api/ciam/profile) | Retrieve a sender's profile | [↗](https://test-nucleus-engine.eks-fincode.com/swagger-ui/index.html?urls.primaryName=customer#/user-management/profileDetails) |

    <Note>
      Subscribe to webhook notifications to receive real-time customer status updates.
    </Note>

    ## Step 2 - Authentication

    Authenticates a user and grants access to the system. Performs comprehensive security checks including email and password validation, IP whitelisting, login security rule enforcement, user status verification, and two-factor authentication when enabled. Upon successful authentication the endpoint returns an `X-Auth-Token` valid for **50 minutes**, shared across all calls within the session.

    | Method | Path | What it does | Swagger |
    |--------|------|--------------|---------|
    | `PUT` | [`securitymanagement/login`](/api/auth/login) [→](/api/auth/login) | Obtain a session token | [↗](https://test-nucleus-engine.eks-fincode.com/swagger-ui/index.html?urls.primaryName=customer#/security-management/login) |

    ## Step 3 - KYC & Compliance

    When a customer is registered, the platform automatically assigns KYC rules based on their risk profile. The compliance checklist may include:

    - Document verification requirements (passport, national ID, proof of address)
    - Transaction limits and thresholds that apply to the customer
    - Identity verification methods (email, phone, eKYC)
    - Risk assessment requirements
    - AML/KYC screening requirements
    - Geographic and delivery method restrictions

    Call `list-organisation-compliance-policy` to retrieve your organisation's KYC policy, then call `customer-compliance-checklist` to find out what actions are outstanding for a specific customer before a transaction can be booked.

    | Method | Path | What it does | Swagger |
    |--------|------|--------------|---------|
    | `GET` | [`compliance/list-organisation-compliance-policy`](/api/ciam/list-organisation-compliance-policy) [→](/api/ciam/list-organisation-compliance-policy) | Retrieve the KYC and transaction rules configured for the organisation | [↗](https://test-nucleus-engine.eks-fincode.com/swagger-ui/index.html?urls.primaryName=customer#/Complaince%20Management%20Service/listComplianceRules) |
    | `PUT` | [`compliance/customer-compliance-checklist`](/api/ciam/compliance-checklist) [→](/api/ciam/compliance-checklist) | Retrieve the pre-transaction compliance checklist for a customer | [↗](https://test-nucleus-engine.eks-fincode.com/swagger-ui/index.html?urls.primaryName=customer#/Complaince%20Management%20Service/preTransactionBookingComplianceCheckList) |

    From here, the flow depends on whether you are using the platform's built-in KYC or your own external KYC provider.

        ### Prerequisites - Plugin setup

        Before using your own KYC provider, you must configure it as a plugin on your agent dashboard.

        1. Go to the **Plugins** section on your dashboard.

        3. Set the **API Type** to **EXTERNAL KYC PROVIDER**.

        If your provider handles email and phone verification as part of its identity flow, also enable the following settings to prevent the platform from sending its own verification messages to the customer:

        - **doNotForwardEmailVerification**: prevents the platform from sending its own email verification link.
        - **doNotForwardPhoneVerification**: prevents the platform from sending its own phone OTP.

        ### Initialise verification with your provider

        Create the verification session with your KYC provider and embed the `reference` from the registration step in the field your provider uses for an external reference. The provider will echo this value back in the webhook it sends to the platform on completion.

        ### Listen for the platform webhook

        After the platform processes the result, it will POST a webhook to your registered callback URL with:

        ```json
        {
          "eventType": "COMPLIANCE_RISK_PROFILE_UPDATED"
        }
        ```

        Check the `customerKycVerificationRecordEntity` array in the payload. Any rule with `"executed": false` is still outstanding and must be fulfilled before the customer can transact.

    ## Step 7 - Pay for a Booked Transfer

    Retrieves the available payment methods for a booked transfer. Returns available methods based on the transaction details, including online card payments, open banking transfers, e-wallets, bank transfers, cryptocurrency, and cash at payment points. The endpoint:

    - Validates the authentication token and user credentials
    - Fetches configured payment gateway integrations for the organisation
    - Calculates payment method charges and fees for each available option
    - Validates transaction amounts against payment method limits
    - Checks compliance requirements and risk profiles
    - Returns metadata for each supported method including fees, totals, and gateway-specific details

    | Method | Path | What it does | Swagger |
    |--------|------|--------------|---------|
    | `POST` | [`paymentmanagement/supported-payment-methods`](/api/deposit-engine/supported-payment-methods) [→](/api/deposit-engine/supported-payment-methods) | List payment methods for a booked transfer | [↗](https://test-deposit-engine.eks-fincode.com/swagger-ui/index.html?urls.primaryName=customer#/payment-management/supportedPaymentMethods) |

    <Note>
      The `X-Idempotency-Key` must be a unique identifier per request. The `pcn` must match the one used in the booking call. Call this endpoint once per transaction - each call returns a new `paymentIntentId`.
    </Note>

    ## Step 2 - Book Transfer with Embedded KYC

    Authenticate as a cashier user and call `create-transaction` with everything embedded. This endpoint reduces the number of API calls required from sign-up to booking. It allows you to combine sender creation, beneficiary creation, and KYC document submission into a single call.

    We recommend calling `customer-compliance-checklist` before `create-transaction` so you can identify and submit any outstanding compliance requirements inline.

    | Method | Path | What it does | Swagger |
    |--------|------|--------------|---------|
    | `POST` | [`transactionmanagement/create-transaction`](/api/transactions/create-transaction) [→](/api/transactions/create-transaction) | Book a transfer on behalf of a sender | [↗](https://test-remittance-service-engine.eks-fincode.com/swagger-ui/index.html?urls.primaryName=customer#/transaction-management/createTransaction2) |

    <Warning>
      This endpoint requires three additional headers: `ipAddress` (the sender's IP address), `X-Idempotency-Key` (a unique key per request), and `Merchant-Host`. A missing header returns HTTP 400 with an empty body.
    </Warning>

    ### Sender options

    Include exactly one of the following in your request:

    - **New sender** - include the sender's personal details (name, email, phone, address, etc.) in the request body. The platform creates the customer record and returns a `customerCode` in the response. Store this code for subsequent calls.
    - **Existing sender** - include `preExistingSenderCustomerCode` with the sender's previously assigned code. All sender fields are resolved from the existing record.

    ### Beneficiary options

    Include exactly one of the following:

    - **New beneficiary** - include the recipient's details in `newRecipientKyc` (name, phone, address, destination country, etc.).
    - **Existing beneficiary** - include the beneficiary's previously assigned code to reuse an existing record.

    ### Embedding KYC documents

    Use the `eligibleDocumentList` field to attach any KYC documents required by the compliance policy. Each entry includes the document type and the base64-encoded file. Pass `associatedRuleId` for each document to link it to the correct compliance rule.

    The response returns a `serverCorrelationId` (the transaction UUID) and a `pcn` (payment reference number) for use in subsequent payment and status calls.

## Supported KYC Providers

Applies to integrations using your own KYC provider. The following providers are currently supported. Your chosen provider must be configured in your agent plugin settings before use.

| Provider | Code |
|----------|------|
| ShuftiPro | `SHUFTI_PRO` |
| SEON | `SEON_IDV` |
| SumSub | `SUMSUB` |
| Didit | `DIDIT` |

### Technical requirements

Your provider must meet all of the following before we can accept their results:

- **ID document verification**: must be capable of verifying government-issued identity documents (passport, national ID, driving licence).
- **Liveness check (face match)**: must perform a biometric face match between the document photo and a live selfie or video capture.
- **Webhook callback support**: must be able to send a webhook to our system when verification is complete.
- **Correlation ID embedding**: must accept and return a reference ID in the webhook payload so the platform can tie the result back to the correct customer record.
- **Structured result payload**: the webhook payload must include verification outcome, document details, and any AML/sanctions/PEP screening results in a structured, parseable format.
